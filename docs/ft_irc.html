First, the basics underneath all of this

Two words everything else depends on: file descriptor, and socket.

File descriptor

When your program opens anything (a file, a socket, a pipe) the OS doesn't hand you the resource itself. It hands you an integer: the file descriptor.

Say opening a file returns 8 (a file descriptor). From that point on, every syscall that touches it refers to it by that one number alone, never by name: write(8, ...) sends bytes to it, close(8) closes it. The filename is never mentioned again, only 8.

Your terminal already gave you three for free: 0 stdin, 1 stdout, 2 stderr. Anything you open yourself gets the next free number.

A connected client is a file descriptor. Same integer, same read/write/close family of operations (sockets use recv/send). That's why one poll() array can watch a listening socket and a dozen clients side by side with the exact same mechanism.

poll() (and its more scalable relatives epoll on Linux, kqueue on BSD) is the function that lets one thread watch many file descriptors at once, asking the kernel "which of these are actually ready right now?" instead of blocking on one at a time. That single call is what the entire non-blocking engine below is built around.

Socket

A socket is one specific kind of thing a file descriptor can point to: a network connection endpoint. socket() is to a connection what open() is to a file. Your server holds two different kinds:

  • The listening socket exactly one, created once, never carries IRC traffic, exists only to produce new fds via accept()
  • Client sockets one per connected person, created fresh each time accept() returns, and these are what actually carry message bytes

What IRC actually is

IRC is the most iconic chat program ever written. It ran most of real-time internet communication through the 90s and into the early 2000s, before people migrated toward more centralized platforms: ICQ, MSN, later WhatsApp.

One of the main things those later programs quietly dropped was the public room. On IRC, if you liked a band, you joined #radiohead. Into skateboarding? You joined #skateboard, made friends, then discovered that #sk8 was about the exact same thing, just way cooler and with way more people on it. That community-building mostly disappeared for two decades, until Discord brought a version of the same shape back, but this time as a centralized service run by a single company, build as Electron app and without IRC's terminal elegance.

IRC, by contrast, is decentralized: no company owns the network, no app store gatekeeps the client, no central database holds everyone's messages. Anyone can stand up their own server. A real IRC network is literally many independently-run servers linked together (server-to-server is half of the protocol). A handful of plain-text commands over one TCP connection is the entire thing.

Communication has since gotten more and more centralized. A handful of companies running the whole stack end to end. Because of that, and because of what that kind of control increasingly means for surveillance, newer projects have been born, circling back to IRC's original idea of decentralization. Matrix is the clearest modern attempt: open, but a far more complex protocol, built for today's surveillance reality, with encryption baked in from the start, the Olm and Megolm cryptographic ratchets, roughly Signal-grade, applied to every room. A nice and a necessary piece of software to have.

IRC, because of its simplicity, is still alive and will always have a place of its own. Pushing 40 years old, it's still the simple, reliable one: Libera.Chat, the network most open-source projects moved to in 2021, alone hosts over 20,000 channels today.

The protocol itself hasn't stood entirely still, either. IRCv3 has layered on things like SASL authentication and capability negotiation, and most networks now support TLS to encrypt the connection. The same idea as HTTPS securing a website, applied to IRC's own wire. IRC isn't trying to do what the newer protocols do; it's doing what it already does best, it's simple and now has just with a layer of security on top.

Writing the client↔server protocol is a good way to learn sockets, non-blocking I/O, and the shape of real-time systems in general. These are the same skills behind a multiplayer game server, a trading system's order feed, or a live chat backend. The mechanism itself is simple: a client opens a TCP connection to a server, picks a nickname, joins one or more channels (chat rooms) and sends lines of text, either broadcast to everyone in a channel or sent privately to one person.

The server's whole job is relaying those lines correctly and enforcing a handful of rules about who's allowed to do what. No images, no video through the protocol itself: just text, one line at a time.

Three simple layers

Three layers, stacked. One that only deals in bytes and fds → Engine (sockets, poll(), recv()). One in the middle that only deals in text and routing → Protocol (parsing, dispatch). One that only deals in the actual rules → Domain (channels, modes, who's an operator).

The clearest way to see it for real is to follow one single action all the way through:

Pedro's JOIN, with the actual bytes

Before any of your code runs, WeeChat (or other IRC client) writes exactly these 11 bytes onto Pedro's socket:

 J   O   I   N   _   #   s   k   8  \r  \n
4A  4F  49  4E  20  23  73  6B  38  0D  0A

That's all: 11 numbers in a kernel buffer. No "JOIN command" exists anywhere yet.

  1. Enginerecv() copies those 11 bytes in. Scans for \r\n, finds it at byte 10. Slices off "JOIN #sk8" and hands that string up. Nothing more, the engine never produces a "JOIN command," only strings.
  2. Protocol, parsing splits the string into Message{ command: "JOIN", params: ["#sk8"] }. Still just reorganized data, nothing has happened yet.
  3. Protocol, dispatch looks up "JOIN" in a table, finds the handler, calls it. Still no logic run, pure routing.
  4. Domain checks this against the real state of the system: does #sk8 already exist, is Pedro allowed to join it, and who's already in the channel who needs to be told he just joined. Here the channel already exists: ssin, schappuy and jkubaev are already in it. So Pedro just becomes a regular member, not an operator, and all three of them get notified that he joined.
One sentence for the Protocol/Domain split: Protocol figures out what was asked; Domain figures out whether it's allowed and what actually changes. Protocol never stores a list of channels — that state lives in Domain alone.

The full chain

We start here: raw TCP bytes. The OS’s network stack already did the real work: handshake, packets and retransmission. From there, ft_irc works in three layers: Engine frames bytes into lines, Protocol turns a line into a command, Domain turns a command into an actual change in the server's state.

Layer 1

Engine

Gets bytes on and off the wire. Doesn't know what a single one of them means.

Engine owns every socket in the project: the one listening socket, which never changes, and one fresh socket per connected client. Its entire job is turning a stream of raw bytes into complete lines on the way in, and turning outgoing messages back into bytes before they’re sent.

Layer 2

Protocol

Turns a line of text into a command and the result back into the exact reply IRC expects

When you type /join #sk8 in WeeChat, this text gets converted (by WeeChat, so the client) to JOIN #sk8\r\n and this is RFC 2812's grammar: command name, space, parameters, terminated by \r\n.

Parsing is the step right after that: turning "JOIN #sk8" into Message{command: "JOIN", params: ["#sk8"]}. Internal to the server, specifically so Dispatch has something to key a lookup on and call the right function with.

Dispatch takes that command name, and maps it to a function pointer, a small object, or whatever you have in your code that actually runs it. Still no logic run yet, just routing.

Layer 3

Domain

The actual rules: channels, membership, modes, who can do what to whom. The end of the chain.

Messaging

How clients and the server talk

The IRC message, the commands we need first, the numeric replies, and one whole conversation, step by step.

1The IRC message

IRC is plain text over TCP. Everything the client sends and everything the server answers is a message: one line of text that ends with \r\n. A message has up to four parts.

prefix
Optional. Who the message comes from: nick!user@host. A client normally does not send one. The server adds it when it passes a message on to the other clients, so they know who spoke.
command
What to do. A word (JOIN, PRIVMSG) or, in the server's answers, a 3-digit number (001, 433).
params
The details the command needs, for example the channel to join or the person to write to. Separated by spaces, up to 15, and none of them can contain a space.
trailing
The last parameter. It starts with : and takes the rest of the line, so it can contain spaces. The : is not part of the text.
size
At most 512 bytes, counting the \r\n at the end.

IRC client (WeeChat)

In an IRC client you don't type the entire message. You type a shorter one, like /join #sk8, and the client translates it into the real message.

IRC client (WeeChat)/join #sk8
→
IRC messageJOIN #sk8\r\n

The server only ever receives the IRC message. In WeeChat you can turn on the display of the raw messages, to see exactly what is sent and received.

WeeChat:/server raw

This opens the raw messages buffer. If your version does not know it, check /help server (newer versions use /irc raw). Close the buffer with /buffer close.

2IRC commands

The command is the word that says what to do: it is the first word of an IRC message (after the prefix, if there is one). /help in WeeChat lists the commands your client knows. IRC has many, the classic ones come from RFC 2812 and newer ones from extensions (IRCv3, for example CAP). We only need some of them, here are examples. Each one shows what you type, the message that is sent, and the server's answer. The server is called oiPoulette.

3Numeric replies

Most replies from the server are messages whose command is a 3-digit number, like 001 or 332. The client reacts to the number. The text at the end is only for people.

  • The number always has 3 digits: 001, not 1.
  • The first parameter is always the nick of the user the reply is for. Before registration there is no nick yet, so the server writes *.
  • The text after the : is for humans. The client looks at the number and at the parameters before it.
  • Numbers from 400 up are errors. The ones below are normal replies.
